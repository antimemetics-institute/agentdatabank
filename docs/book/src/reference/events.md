# Events

**If your experiment is written in Python, use the `adb_events` library:**

```python
from adb_events import Metric, Status, emit

emit(Metric(name="score", value=1))
emit(Status(detail="Starting evaluation"))
```

**For experiments written in other languages, invoke the `adb-emit` CLI directly:**

```sh
adb-emit metric --name score --value 1
adb-emit status --detail "Starting evaluation"
```

Both APIs validate events, deliver them to the runner, and report delivery
errors. To execute an experiment, use its named app (for example,
`nix run .#inspect-hello -- ...`) or launch it from `adb-local`. The generated
experiment launcher starts the runner and configures event delivery. Do not
invoke `adb-runner` or the underlying experiment program directly to start a run,
and do not implement a socket client in experiment code.

The experiment program's stdout and stderr are captured as text, including printed JSON. The
runner supplies the transport configuration automatically. See
[emission tools](#emission-tools) for CLI flags and
[Python emission](protocol.md#how-can-python-experiments-emit-validated-events)
for model construction.

Each run stores event envelopes in `events-NNNNN.jsonl`. The runner owns the
envelope and lifecycle events. The following sections describe the saved format
and event vocabulary.

## Transport

```json
{"v":0,"ts":"2026-01-01T12:00:00.000Z","run":"RUN_ID","seq":0,"event":{"type":"metric","name":"score","value":1}}
```

| Envelope field | Meaning |
| --- | --- |
| `v` | Transport version; currently `0`. |
| `ts` | UTC capture timestamp from the runner. A producer timestamp can be included inside the payload. |
| `run` | Run ID. |
| `seq` | Zero-based sequence number increasing within the run. |
| `event` | Original payload object. |

Payloads use the closed set of types below. Unknown types, missing types, undeclared fields and malformed payloads are invalid. The runner rejects invalid socket submissions. All captured stdout/stderr remains text inside standard events, so saved records conform to the [typed Python reader](protocol.md#reading-runs-in-python). Put experiment-specific JSON inside `CustomEvent.data` or `AgentEvent.data`.

## Lifecycle events

These types are generated by the runner. Experiments must not use the `run.` prefix for their own types.

| Type | Fields |
| --- | --- |
| `run.start` | `condition`, `experiment`, `source`, `fetch_ref`, `dirty`, `spec_params`, `realized_params`, `seed`, `replicate`, `env`, `result_definitions` |
| `run.status` | `state`; currently emitted when entering `running` |
| `run.end` | `state`, `duration_s`, `summary`, `usage_totals`, `exit_code` |

`run.start` records the identity, inputs and derived run seed described in [run files](layout.md). `spec_params` is the bound condition input; `realized_params` is passed to the process. They are currently identical. Its `env` records `adb_runner` (runner version) and `platform` (operating system and machine architecture), not a complete environment snapshot.

`result_definitions` snapshots the manifest's normalized [result declarations](manifest.md#result-declarations), including labels, descriptions, details and units when supplied. The same definitions are saved in `run.json`.

`run.end.summary` contains the final valid metric value for each emitted name. `usage_totals` contains `llm_calls`, `input_tokens` and `output_tokens`. `exit_code` is the child process return code; negative values identify signal termination. An incomplete stream may have no `run.end`.

## Status and logs

| Type | Required fields | Optional fields |
| --- | --- | --- |
| `status` | `detail`: human-readable activity description | — |
| `log` | `message`: log text | `level`: `debug`, `info`, `warn` or `error`; default `info` |
| `stdout` | `line`: captured stdout text | — |
| `stderr` | `line`: captured stderr text | — |

`status` describes experiment progress and does not change the lifecycle state. `stdout` and `stderr` are generated by process capture and have no inferred severity.

## Metrics

A `metric` has required `name` and `value`, with optional `step` (integer) and `unit` (string).

`value` must be a number, string or boolean. Flatten structured metrics into separate names using `/`, for example `accuracy/easy` and `accuracy/hard`. Metric names identify run-level values. Re-emitting a name updates its displayed and summary value to the last emission; all earlier events remain stored. `step` records position but does not create separate summary keys.

Use instance scores for per-item evaluation results rather than repeatedly emitting one run-level metric name for unrelated items.

## Messages

A `message` records communication in the experiment.

| Field | Meaning |
| --- | --- |
| `from` | Required sender name. |
| `content` | Required text content. |
| `channel` | Required conversation or context label. |
| `to` | Optional recipient. |
| `visible_to` | Optional list describing which participants could see the message. This is experiment metadata, not viewer access control. |
| `meta` | Optional object for role, instance attribution and other context. |

## Model calls

An `llm.call` records a model request and its available outcome.

| Field | Meaning |
| --- | --- |
| `model` | Required requested model ID. |
| `request` | Required request object containing `messages` (array of message objects) and optional `params` (effective SDK arguments, object, default empty), `model` (SDK model argument) and `raw` (provider request object). |
| `agent` | Optional agent making the call. |
| `response` | Optional response object; see below. |
| `usage` | Optional object with nullable integer `input_tokens` and `output_tokens`. |
| `latency_ms` | Optional elapsed call latency in milliseconds. |
| `error` | Optional object with required `kind` and `message` strings. |
| `meta` | Optional attribution and contextual metadata. |

A response contains required `message` (an object) and optional `finish_reason`, `model` and `raw`. Response `model` records the provider-returned model ID when available, which may differ from the requested alias. `raw` retains a provider-specific response object where the adapter supplies it. Message objects inside requests and responses are open objects so adapters can retain tool calls and other provider fields.

Missing usage or response fields mean the record did not supply those values. They do not imply that a call was free or that the provider produced no response. Check `error` and the adapter's records when diagnosing a failure.

## Agent events and instances

An `agent.event` has required `agent` and `kind` strings, plus a `data` object defaulting to empty. Use it for experiment-specific actions and structured results that do not fit another standard type.

The `instance` event closes out one independent unit of work within a run, such as a dataset item or match:

```json
{"type":"instance","agent":"solver","data":{"id":"item-12","repeat":1,"scores":{"accuracy":1},"error":null}}
```

| `data` field | Meaning |
| --- | --- |
| `id` | Instance identifier, string or integer. |
| `repeat` | Optional one-based repeat of this instance within the run. This is separate from the run-level replicate. |
| `scores` | Optional flat object mapping score names to numbers, strings or booleans. Flatten structured score names using `/`. |
| `error` | Optional error description for this instance. |
| `target` | Optional target value. |
| `meta` | Optional object for additional experiment context. |

The Python `Instance` and `InstanceData` models validate the ID, positive repeat and scalar scores. Messages for an instance conventionally use channel `instance:ID`; messages and model calls carry `meta.instance_id` and optional `meta.repeat`. This attribution keeps interleaved instances distinguishable.

The viewer renders instance outcomes and derives aggregate displays from their scores.

## Custom events

A `custom` event has a required `kind` string and a `data` object containing
JSON values. Use a descriptive, namespaced kind for experiment-specific data
that does not fit another standard event:

```json
{"type":"custom","kind":"govsim.state","data":{"round":1,"resource":42}}
```

These records deserialize as `CustomEvent` in every consumer. The contents of
`data` remain generic JSON; a kind does not register another model or schema.

## Artifacts

An `artifact` points to a file retained by the experiment.

| Field | Meaning |
| --- | --- |
| `name` | Required display name. |
| `path` | Required path relative to the run directory, normally `artifacts/FILENAME`. |
| `media_type` | Optional MIME type. |
| `bytes` | Optional file size in bytes. |

The event does not copy or create the file. The producer must write it before emitting the pointer. The Python helper `adb_experiment.scaffold.deposit_artifact` performs both steps for text files.

## Emission tools

`adb-emit` validates a producer payload, sends it to `ADB_EVENT_SOCKET`, and waits for acknowledgement. It is installed in the runner package, alongside `adb-runner`. The following checkout commands only inspect a schema; they do not launch an experiment:

```sh
nix-build -A adb-runner
./result/bin/adb-emit schema llm.call
```

In the experiment program, invoke `adb-emit metric --name score --value 1` to record a value.

`adb-emit schema` prints schemas for all standard payload types, while `schema TYPE` selects one. `schema --union` exports the discriminated payload union; `schema --envelope` exports the complete saved record. The helper offers these emission subcommands:

| Subcommand | Fields accepted as flags |
| --- | --- |
| `status` | `--detail` |
| `log` | `--message`, `--level` |
| `metric` | `--name`, `--value`, `--step`, `--unit` |
| `message` | `--from`, `--content`, `--channel`, `--to`, `--visible-to`, `--meta` |
| `llm-call` | `--agent`, `--model`, `--latency-ms`, `--request`, `--response`, `--usage`, `--error` |
| `agent-event` | `--agent`, `--kind`, `--data` |
| `custom` | `--kind`, `--data` |
| `instance` | `--agent`, `--data` |
| `artifact` | `--name`, `--path`, `--media-type`, `--bytes` |

Hyphenated `llm-call` and `agent-event` subcommands emit dotted wire types. JSON-valued flags take JSON text; `--value` accepts JSON or a bare string, and `--visible-to` accepts comma-separated names. `llm-call` also accepts a payload body object on stdin, with flags overriding fields from stdin. Invalid standard payloads return status `2` and print an error to stderr.

Python producers construct Pydantic event models and call `emit(event)`; see [process protocol](protocol.md#how-can-python-experiments-emit-validated-events). Only the public producer classes are accepted by `emit`. Unknown constructor fields raise; explicit metadata objects preserve provider and experiment fields. Use `CustomEvent` for generic experiment data.
